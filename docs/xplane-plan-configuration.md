# Plan-sourced xplane configuration

Set `SpectrumXRailPoolConfig.spec.dmsPlanParamsRef` to a DMSPlanParams in the pool's namespace. Its selector must cover every pool node. The structured blueprint must select the `spcx-doca-xplane-boot` service and a supported ra22 or ra24 TOML artifact for `host-k8s`.

After the existing local switchdev and OVS bridge preparation, the host controller compiles the plan with dms-lib and writes the selected service bytes unchanged to `/var/lib/spectrum-x/plans/<pool-uid>/xplane.toml`. The existing xplane DaemonSet mounts that local file and starts xplane with `--config`. The file mount requires the file to exist on a host before its xplane pod can start there. Pools without the reference retain the existing DaemonSet arguments and OVS-derived configuration.

The authored TOML determines topology authority. The release image reads topology from OVSDB when configuration interfaces are absent, and reads topology from configuration when interfaces are present. To preserve the existing OVSDB topology source, author the blueprint artifact without an interfaces section. The operator does not rewrite the selected service bytes. The blueprint must also match the pool's existing OVS topology if it supplies interfaces; bare-metal VF representor topology does not match the Kubernetes patch ports.

Configuration is read at xplane startup. Reconciliation updates the host file atomically, but does not restart running pods or claim live reload. A new pod with a fresh hostPath mount reads the current file. Restarting a process inside an existing container may continue to see the old mounted inode. Reload behavior has not been established for the release image. An invalid plan, missing service artifact or write failure returns an error before the shared DaemonSet is changed. There is no cross-host staging or readiness protocol; the existing DaemonSet and its rolling update strategy remain the service lifecycle. On first enablement, the shared DaemonSet may roll a peer before that peer has written its file. Its replacement pod then waits on the required File mount, which can temporarily reduce availability. This matches the scope of an ordinary DaemonSet change, not a zero-disruption guarantee.

The release baseline is Network Operator v26.10.0-rc.3 with xplane image `nvcr.io/nvstaging/doca/xplane:3.6.0057`. A previous version of this PR was qualified on mevo-carmel with an immutable bundle and per-host receipts. That result does not qualify this reduced delivery path or live configuration changes. It also does not establish that config-supplied interface topology is equivalent to OVSDB-derived topology.
